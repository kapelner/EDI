# Feasibility Report: Dependent Censoring × Interval Censoring

## Status

Commissioned by TODO-10 in
`package_metadata/finished_features/interval_censored_survival_response.md`
("Commission a follow-up feasibility report scoping how dependent censoring
(`InferenceSurvivalDepCensTransformRegr`) and interval censoring compose,
before writing any implementation TODOs for it"). This is a scoping
document, not an implementation plan — its job is to determine whether
implementation TODOs can responsibly be written at all, and if so, what
they should say.

**Bottom line: no implementation TODOs should be written yet.** This is
not an engineering gap with a known closed-form fix (Tier 1) or a
known-harder-but-well-defined generalization (Tier 2/the other two Tier-3
reports). It is a genuine identifiability question: under the standard
definition of interval censoring used by the rest of this plan (periodic
inspection times, not a competing censoring event), there may be no
well-posed dependent-censoring analog to extend to at all. Below is why,
and what would need to be true before this became actionable.

## What `InferenceSurvivalDepCensTransformRegr` Actually Fits

`R/EDI/R/inference_survival_dep_cens_transform.R`, backed by
`DepCensTransformLikelihood`
(`R/EDI/src/fast_survival_models_optim.cpp:208-330`) and
`fast_dep_cens_transform_optim_cpp`. The model is a **bivariate
log-normal AFT with a Gaussian-copula dependence structure between the
event time `T` and an unobserved, latent censoring time `C`**:

```
log T = X beta_event + sigma_event * Z1
log C = X beta_cens  + sigma_cens  * Z2
(Z1, Z2) ~ BivariateNormal(0, 0, 1, 1, rho)
```

Both `T` and `C` are modeled as regression outcomes with their own
coefficient vectors (`beta_event`, `beta_cens`), their own scale
parameters (`sigma_event`, `sigma_cens`), and a correlation `rho` (fit on
the `atanh` scale) capturing the *dependence between the event and the
censoring mechanism*. The observed data is `y = min(T, C)`, `dead =
1{T <= C}`. The per-subject log-likelihood
(`fast_survival_models_optim.cpp:259-274`) is:

- If `dead = 1` (event observed at `y`): `log f_event(y) + log
  P(C > y | T = y)` — the event density times the *conditional* survival
  of censoring given the observed event time, using the Gaussian
  conditional-normal formula (`w_event = (rho*z_event - z_cens) /
  sqrt(1-rho^2)`, `log_S_cond_cens = log Phi(w_event)`).
- If `dead = 0` (censored at `y`): `log f_cens(y) + log P(T > y | C = y)`,
  the mirror image.

This is the standard closed-form **Gaussian-copula dependent-censoring
AFT model** (the same construction underlies, e.g., Emura & Chen's
copula-based dependent-censoring survival literature, and Deresa & Van
Keilegom's copula-AFT work on informative censoring). Its entire point is
that `T` and `C` are *both modeled as latent random times whose joint
distribution is estimated from the data* — the correlation `rho` is a
free parameter, not assumed zero as ordinary (independent) right-censored
survival analysis assumes.

`InferenceSurvivalDepCensTransformRegr` does not override
`supports_interval_or_left_censored_data()`
(confirmed via `grep`), so it inherits the `Inference` base class default
of `FALSE` and hits the same `stop()` guard as every other unextended
survival class in this plan
(`inference_all_abstract.R:51`, `Inference$initialize()`) when given
interval-censored data today — the correct, fail-loud current state, not
a bug.

## Why This Is An Identifiability Question, Not An Engineering One

The other two Tier-3 classes (Clayton copula, rank regression — see the
sibling feasibility reports) have a well-defined *target*: a closed-form
or estimating-equation extension of the same likelihood/objective that
handles an interval `[L, R]` in place of a point `y`. The generalization
is algebraically harder but conceptually unambiguous — "what is
`P(L <= T <= R)` under this model" always has a definite answer.

Dependent censoring does not have that clean target, for a structural
reason: **the entire model's reason for existing is that `C` is a random
variable jointly distributed with `T`.** Interval censoring, as scoped
throughout the rest of `interval_censored_survival_response.md` (see its
own opening framing — periodic-visit inspection producing `[y_L, y_R]`
windows rather than a continuously-observed clock), is not generated by
a competing random time `C` at all. It is generated by a *deterministic
or design-controlled inspection schedule* (visit at month 6, visit at
month 12, ...). The two censoring mechanisms this class and this plan
each assume are different things:

- **This class's assumption:** censoring is a latent race between `T`
  and a random `C`, and `(T, C)` are dependent (correlated) draws from a
  joint distribution. The whole model exists to estimate that
  dependence, because pretending `rho = 0` (independence) when it's
  really nonzero silently biases the treatment effect.
- **Interval censoring's actual generating mechanism (per this plan):**
  the observation window `[L, R]` comes from a schedule of inspection
  times, not from a "when would this subject have dropped out"
  distribution. There is no natural `C` at all in the visit-schedule
  picture — only `L` and `R`, the two most recent bracketing inspection
  times.

So composing the two requires first answering a question this document
cannot answer with certainty from the code alone, and that a real
feasibility pass would need to resolve with the package's actual
domain/study context in mind: **in the data this package's users
actually have, is there a real, separately observable (or at least
model-able) censoring-time process that is itself only interval-observed
— i.e., is "dependent + interval" describing dependence between the
*event* time and the *inspection schedule* itself (informative visit
timing, a well-studied but distinct topic — see, e.g., the "informative
observation times" longitudinal-data literature), or is it describing
something closer to what this class already does (a genuinely
random, correlated competing time) that merely happens to also be
imprecisely observed?** These are different models with different
identification strategies; picking the wrong one produces a technically
implementable but conceptually meaningless extension.

## What Would Have To Be True Before Writing Implementation TODOs

1. **A concrete target likelihood, stated in closed form**, analogous to
   how Tier 1's `log(S(L) - S(R))` extension is stated in
   `interval_censored_survival_response.md`'s own Tier 1 section. For
   this class that would mean specifying `P(L <= T <= R, \text{dead
   status})` under the bivariate `(T, C)` copula model *given whatever
   the resolved interpretation of "interval + dependent" turns out to
   be* (informative-inspection-time model vs. an interval-observed
   competing-time model — these have different likelihoods and neither
   is a small edit of `DepCensTransformLikelihood`'s current four-branch
   `if (dead)` structure, which fundamentally assumes a single observed
   `y` per subject with a binary `dead` flag, not an interval).
2. **An identifiability argument.** Dependent-censoring models are
   already only identified under strong parametric assumptions (the
   bivariate log-normal / Gaussian-copula form here is itself a modeling
   choice, not something the data alone determines — this is well known
   in the dependent-censoring literature). Adding interval observation on
   top removes information the model needs to estimate `rho` at all; a
   real feasibility pass should check whether `rho` remains identified
   under plausible interval widths, ideally via a small simulation, before
   any implementation work starts.
3. **A literature check for existing estimators**, the way Tier 2 found
   `icenReg`/`interval` as ready-made delegation targets. A cursory look
   turned up no obvious single dominant R package combining dependent
   *and* interval censoring under a copula-AFT structure the way `icenReg`
   covers interval-censored Cox/AFT under independence — this needs a
   dedicated literature search (informative-censoring + interval-censoring
   intersection specifically), not an assumption either way, before
   concluding whether this is a from-scratch build or another delegation
   opportunity.

## Recommendation

Do not write implementation TODOs from this report. Instead, the next
concrete step (if this is prioritized) is a modeling-scoping
conversation — with the package's actual users/domain experts, not just
the codebase — to pin down which of the two composition stories above (or
a third one) actually matches real data this package is meant to serve.
Once that's settled, a second, narrower feasibility pass can specify the
target likelihood and check identifiability, and *that* pass is what
should produce implementation TODOs.
